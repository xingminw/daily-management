# Daily Management：项目上下文与当前决策

> 状态日期：2026-08-19  
> 本文件记录当前讨论背景、已经验证的事实、尚未验证的问题与下一步计划。它不应包含密码、Token、授权码、App Secret、Cookie 或个人账号 ID。

## 1. 项目目标

把本仓库维护成一个个人日常事务管理与外部工具连接中枢，使 Codex 能通过稳定、可检查、可审计的方式连接国内常用办公系统，而不必依赖某个单一软件的 UI。

当前关注的事务包括：

- 日历与日程管理
- 学校邮箱的收取、搜索、整理与回复
- 学校通知、审批、考勤和组织通讯录
- 待办与任务管理
- 钉钉、飞书、腾讯会议等会议工具
- 文档、云盘和会议纪要
- 后续的每日摘要、会前准备和会后行动项等自动化

这个 repo 应保存连接代码、适配器、配置模板、测试、操作规则与决策记录，不保存邮件正文、聊天记录、真实账号配置或认证凭据。

## 2. 用户与组织背景

- 学校官方办公生态是钉钉。
- 钉钉与学校通知、组织身份、审批、考勤等正式流程存在天然关联。
- 用户主观上认为钉钉的部分体验不够好，但目前还不清楚它的开放能力是否足以承担个人管理中心。
- 飞书使用体验较好，而且官方 `lark-cli` 的 Agent 支持已经验证可用。
- 如果钉钉可以可靠覆盖核心需求，优先只维护钉钉，避免额外维护飞书账号、日历和同步关系。
- 学校邮箱大概率必须接入，但它可能是独立邮件服务器，不应默认认为“钉钉邮箱”就是学校邮箱。

## 3. 当前核心问题

在正式决定架构前，需要回答：

> 钉钉是否能在当前学校组织和当前个人权限下，覆盖日历、邮件、任务、消息、审批、考勤、文档、会议与自动化等核心需求？

这里必须区分三件事：

1. 钉钉产品客户端里是否有这个功能。
2. 钉钉官方 CLI/OpenAPI 是否暴露了这个功能。
3. 当前学校组织是否授权当前用户通过 API 实际访问这个功能。

“官方文档存在接口”不等于“当前账号能调用”。最终选型应以真实账号的只读和最小写入测试结果为准。

## 5. 需求优先级

### P0：必须解决

1. 能稳定查看和管理个人日程。
2. 能接入学校邮箱，至少支持安全登录、收件箱列表、搜索和单封读取。
3. 能查看学校组织里的正式信息，例如通知、审批、考勤或组织联系人。
4. 任何连接失效时能通过 `doctor` 或类似命令快速定位问题。
5. 凭据不得进入 Git；写操作必须可预览、可确认、可审计。

### P1：高价值

1. 创建、修改日程并查询闲忙。
2. 邮件分类、摘要和回复草稿；发送前必须确认。
3. 查看、创建和完成待办。
4. 搜索钉钉消息、文档、云盘和会议纪要。
5. 将邮件或会议内容转成日程、任务和行动项。
6. 生成每日摘要和会前准备材料。

### P2：后续扩展

1. 会议录制、转写和会后总结。
2. 腾讯会议等外部平台同步。
3. 事件订阅和后台自动化。
4. 多账号、多组织和跨平台同步。

## 7. 建议的测试顺序

### 阶段 A：认证与权限基线

1. 完成 `dws auth login`。
2. 执行 `dws auth status --format json`。
3. 执行 `dws doctor --format json`。
4. 执行 `dws profile list --format json`，确认学校组织和个人身份。
5. 只记录权限结果和错误类型，不记录 Token、corpId、userId 等个人标识。

### 阶段 B：只读覆盖测试

按以下顺序执行真实只读查询：

1. 当前用户与组织 profile。
2. 今日日程与可见日历。
3. 我的待办。
4. 邮箱身份与邮件搜索能力。
5. 我的待审批和已发起审批。
6. 自己的考勤记录。
7. 可见通讯录范围。
8. 文档、云盘、听记和知识库列表。
9. 消息搜索和个人事件订阅能力。

所有命令使用结构化 JSON 输出；发现权限缺失时不猜测、不绕过，记录需要的 scope 和管理员动作。

### 阶段 C：最小写入测试

只读测试完成后，再由用户逐项确认是否执行：

- 创建一条可识别的临时日程。
- 创建一条临时待办。
- 创建一封邮件草稿或执行发送预览，不直接发送。
- 给测试群或自己发送测试消息。

删除、撤回、取消日程等操作属于高风险操作，必须在执行时再次确认。测试数据应明确标记，并在用户确认后清理。

### 阶段 D：形成结论

为每项能力记录：

- 可用：当前个人账号可直接使用。
- 需授权：接口存在，但需要学校管理员或额外 scope。
- 不可用：当前组织或账号无法使用。
- 不适用：学校没有启用该钉钉产品。
- 需外部适配：例如独立学校邮箱或腾讯会议。

## 8. 架构候选

### 方案 A：钉钉作为唯一中心

适用条件：钉钉真实测试能够覆盖日历、待办、正式学校流程和邮件，且权限稳定。

优点：

- 只维护一个主生态。
- 与学校组织身份、通知、审批和考勤天然一致。
- 减少跨平台同步和冲突。

风险：

- 个人账号能否获得 API 权限取决于学校组织。
- 钉钉邮箱不一定等于学校独立邮箱。
- 视频会议开放能力可能不完整。

### 方案 B：钉钉为主，学校邮箱直接接入

适用条件：钉钉覆盖学校流程与个人日历，但学校邮箱是独立服务器。

组成：

- 钉钉：日历、待办、通知、审批、考勤、通讯录。
- IMAP/SMTP 或学校官方协议：邮件。
- 本 repo：统一命令、策略和自动化。

这可能是当前最有希望的低维护方案。

### 方案 C：钉钉负责学校生态，飞书负责个人管理

只在以下情况采用：

- 钉钉个人日历或待办 API 无法授权。
- 钉钉 CLI 稳定性不足。
- 飞书体验优势足以抵消双平台维护成本。

该方案需要明确单向同步方向，避免日程重复和循环更新。

## 9. 邮箱接入判断

邮箱不能仅根据 CLI 中是否出现 `mail` 命令来决定。需要确认：

- 学校邮箱域名与实际服务商。
- 是否开放 IMAP/SMTP。
- 是否使用普通密码、应用专用密码、OAuth 或统一身份认证。
- 是否支持服务器端搜索、草稿和文件夹。
- 钉钉邮箱是否已绑定或托管学校邮箱。

默认技术优先级：

1. 标准 IMAP/SMTP + TLS。
2. 学校邮件服务商提供的正式 API/OAuth。
3. 钉钉邮箱接口（仅当确认学校邮箱实际在钉钉中可访问）。
4. 网页自动化作为最后手段。

## 10. 安全与维护原则

- Git 中不得出现密码、Token、Client Secret、Cookie、授权码或真实账号 ID。
- 优先使用官方 CLI，并固定版本、保留升级与回滚路径。
- 所有读取命令输出 JSON，便于审计和测试。
- 所有写操作先使用 `--dry-run` 或等价预览。
- 发送邮件、发消息、创建日程等代表用户对外行动的操作，执行前确认目标和内容。
- 删除、撤回、取消会议、拒绝审批和修改权限必须再次明确确认。
- 平台连接应提供 `doctor`、认证状态和权限诊断。
- repo 保存的是连接能力和工作流，不是个人数据仓库。

## 11. 当前结论

现在还不能断言“钉钉可以完全替代飞书”，也不能断言“钉钉不够用”。

目前最重要的新信息是：钉钉已经有面向 Agent 的 `dws` CLI，能力表面覆盖范围很广，甚至包含日历、邮箱、审批、考勤、文档和会议纪要。真正的限制很可能来自学校组织授权，而不是 CLI 本身。

因此当前决策是：

1. 暂不继续实现邮箱适配器。
2. 暂不把飞书确定为主日历。
3. 先完成钉钉 OAuth、profile 与只读能力审计。
4. 根据真实权限结果，在方案 A、B、C 中选择。

## 12. 下一步

下一步从以下命令开始，并坚持只读：

```bash
dws auth status --format json
dws doctor --format json
dws profile list --format json
```

若尚未登录，则重新执行：

```bash
dws auth login --device --format json
```

登录完成后，逐项执行第 7 节的只读测试矩阵，并把结果追加到本文件或单独的 `docs/dingtalk-capability-audit.md`。
